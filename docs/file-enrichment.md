# Incremental file enrichment contract

This is the production design for the filesystem enrichment work following the bounded September 2026 survey. It defines ownership and evidence rules; it does not describe an installed scheduler or authorize a corpus run. The existing [file catalog](file-catalog.md) remains the curated observation store, and [sinnix-fs](filesystem-index.md) remains the directory/content inventory and judgment-ledger owner.

## Owner and persistence

`sinnix-fs` is the sole production owner of the extraction cache and work manifest. Its implementation belongs beside the filesystem index under `pkgs/sinnix-fs/`, with private runtime data under `/realm/state/fs-index/enrichment/`. Versioned manifest generations, extraction artifacts, and receipts live there, with restrictive permissions; a manifest generation is immutable after publication. A new generation reconciles current inventory and prior results, while a failed or interrupted generation remains available for audit. The cache is rebuildable from source bytes and extractor recipes. The manifest and receipts preserve work history and must survive a cache eviction. Neither belongs in Git, the curated catalog JSON, the judgment ledger, or an AgentCTL run ledger. Retention and backup policy for the private state directory must be declared before production enablement; cache eviction must leave referenced inspection evidence intact or mark its locator unavailable.

The scanner supplies candidate paths, stat identity, full or sampled fingerprints, and explicit collection boundaries. The enrichment owner plans work and stores stage receipts. The catalog owns reviewed file and collection annotations and inspection coverage. The judgment ledger owns attributed classification decisions. Native applications own their records, revision IDs, and payload queries. Lynchpin may consume owner-issued references for cross-source analysis; it does not schedule extraction or replace any owner's state. AgentCTL queues declared operations and supplies job results, not item-level truth. No new asset registry is introduced.

## Identity and invalidation

Each manifest row has a logical key, source owner, source revision, requested surface and depth, and a work-generation ID. Logical keys identify a *place in an owner's namespace*, not equal bytes:

| Item | Logical key | Source revision and validation |
|---|---|---|
| Regular file | `file:` plus the scanner's canonical absolute path and source namespace | Record lstat/fstat device, inode, size, nanosecond mtime, mode and a full SHA-256 when available. Recheck before and after reads. A verified rename may link the old catalog UUID through `relocate`; a reused path with different identity is a new source version needing explicit reconciliation. |
| Archive member | Parent file logical key plus normalized member path and occurrence index | Parent archive full digest or explicit stat revision, then member size/CRC if supplied and a full digest of decompressed member bytes. Reject traversal paths, duplicate names without an occurrence index, encrypted or unbounded expansion. A changed parent invalidates the member even when its name persists. |
| Native record reference | Owner namespace, stable owner record ID and owner-issued revision token | Query the native owner for that revision and its evidence locator. If the owner cannot supply stable ID, revision, and scoped read, retain `native-boundary` and do not copy its private database into the generic scanner. |

A full digest proves byte identity only for the bytes actually hashed. The scanner's `sample_sha256` (`sha256-head-tail-size-v1`) is a candidate fingerprint, never a deduplication certificate, a cache content key, or evidence that a changed file can skip work. A stat tuple is a revision hint subject to races and reuse. When full hashing is unavailable, cache reuse is restricted to the same logical key and unchanged checked stat identity, with a fresh before/after check; it is recorded as provisional and cannot support cross-path reuse. Unknown schema or malformed digests invalidate reuse.

The deterministic extraction key is `(source owner, logical key, certified source revision or provisional stat revision, extractor name/version, options, selected ranges, output schema version)`. The semantic observation key adds `(extraction artifact digest, requested scope/depth, semantic schema version, prompt version, model identity and model revision where available)`. Changes to any component require a new stage result; prior receipts remain history. A new prompt does not require re-extraction when its exact artifact and recipe still validate. A source change invalidates both stages. A review correction is a new attributed observation, never an in-place rewrite of an earlier inspection. Cache hits must revalidate the source revision and report the prior artifact's evidence locator; missing or stale artifacts become pending work.

## Manifest and coverage

A generation has an explicit discovery scope: roots, exclusions, scan version/time, file types, size limits and native boundaries. Each logical item appears once within that generation and has one current state. State transitions append receipts with attempts and errors; retry or changed source revision creates a new attempt. Counts use the generation's disjoint logical keys, not overlapping catalog collection counts.

| State | Meaning and coverage |
|---|---|
| `discovered` | In scope and identified, with no valid extraction or inspection for the requested depth. Counts as pending. |
| `extracted` | A deterministic artifact exists with recipe, exact ranges, source revision and validated digest. Semantic inspection remains pending. An empty or truncated artifact does not imply complete reading. |
| `inspected` | A reviewed semantic observation names exact source surfaces, locators, extraction evidence, and coverage (`complete` within stated surface or `sampled`). It may be imported into the catalog; inspection is not a claim about omitted pages, dynamic content, linked works or OCR quality. |
| `failed` | An attempted stage returned a typed error, with stage, retryability and evidence. It is neither inspected nor silently skipped. |
| `deferred` | Work was intentionally postponed with reason, responsible decision, requested depth and revisit condition. Unsupported format, budget limit and missing access are distinct reasons. |
| `native-boundary` | Generic traversal stopped at an owner boundary. Record owner and adapter status, without a fabricated descendant count. Owner-issued records become separate manifest items only through an adapter. |

These are mutually exclusive current states. Historical stage receipts remain attached, so a failed inspection can retain an earlier extraction without counting as `extracted` in the current-state totals. Report denominators as discovered in-scope logical items plus explicitly listed unknown or unenumerated boundaries. An unreadable branch has unknown descendants, never zero. `inspected` is split by complete/sampled scope, and its count is not the catalog's collection-level `coverage` count. The catalog's `complete` requires its own stated known denominator and matching inspected count. The ledger's inherited SQL `coverage` is classification coverage, not this work metric.

## Stages, evidence and resumption

Deterministic extraction emits bounded text, document metadata and structural locators such as file line, PDF page, EPUB spine/member and paragraph, HTML block or JSON Pointer, image frame/region, and OCR page/region. Its artifact records extractor and output schema versions, source revision, selected ranges, truncation, errors, bytes/characters and artifact SHA-256. Model inspection consumes a fixed artifact or image evidence packet and emits attributed semantic fields, claims, uncertainty and source locators under a versioned schema/prompt/model identity. An extraction locator identifies the exact derived bytes; a semantic locator points back to the source surface and to that extraction artifact. Visual inspection and OCR are separate evidence channels. The deterministic serializer adds mechanical identity and coverage fields after validating model output.

A work attempt claims a row by `(generation, logical key, source revision, requested depth)` with an expiring lease and fencing token. Committing a receipt requires the current token and revalidated source revision; a stale worker cannot overwrite a newer result. Repeated identical receipts are idempotent. On restart, expired leases return to pending and completed stage receipts are reused only after the invalidation checks above. Concurrent workers write isolated artifacts, then the owner atomically publishes validated receipts. No worker imports directly into the curated catalog or ledger. A coordinator reviews observations and imports one reconciled batch with catalog `--on-conflict record`; conflicting annotations retain attribution. Judgment imports use the ledger's locked, idempotent `judgments import` and expected ledger SHA-256 when based on a reviewed snapshot. The import receipt links manifest item, catalog UUID or ledger record hash, source revision and inspection evidence. A changed catalog identity or ledger head pauses reconciliation instead of silently rebinding history.

## Specialist routes

| Route | Supported surface and defer condition |
|---|---|
| HTML and embedded JSON | Parse saved HTML as inert input. Visible prose extraction excludes scripts/styles, while a separately versioned structured-data parser may read a recognized embedded `application/json` block with schema, JSON Pointer and count checks. A static shell alone is sampled or deferred for its dynamic content. Never execute page JavaScript or fetch links to claim completeness. Unknown embedded schemas are deferred. |
| Encrypted documents | Detect encryption and report a typed `failed` extraction with tool error and page count if available. Retry only with an authorized owner-supplied credential route; do not guess passwords or invent contents. Access policy or missing credential can then defer a new attempt. |
| Images | Record bounded metadata separately from a direct visual inspection of stated frame(s)/regions. Source EXIF dates remain claims. A whole frame may be visually inspected while embedded text remains unreadable; ambiguous objects or intent remain uncertain. Unsupported size/codec or absent visual review is deferred. |
| OCR | Run only for specified raster pages or image regions when text is needed and direct text is absent or insufficient. Record engine/version, language, page/region, confidence or quality limit and text locator. OCR is supplemental evidence and never silently upgrades visual or document coverage; expensive whole-book OCR requires a separately approved budget. |

Archive formats also require expansion limits, safe member paths and per-member provenance. An unrecognized archive or unsafe member is deferred or failed with its reason, without claiming its descendants were inspected.

## Pilot bounds and migration

The selected September 2026 wave inspected 238 of 239 files; one encrypted PDF failed. It reported 188 complete reads within their stated surfaces, 50 sampled reads, 3.23 million extracted characters, 695 anchored claims and 606 retrieval questions. Sixteen worker sessions spanned 21.7 minutes, excluding coordinator preparation and publication. Harness counters reported 34,964,589 input tokens (33,170,432 cached) and 355,962 output tokens. These are session observations, not billing receipts or a monetary price. The 239 selections were a deterministic spread from bounded roots and formats, not a random whole-filesystem sample. Native records, large archives and most media were outside its denominator.

Start production trials with 20–40 short documents or one coherent large work per semantic packet, then cap actual extracted tokens and duration from a measured dry run. For the first comparable 40-item trial, require review before exceeding 300,000 uncached input tokens or 60,000 output tokens across workers, and record total and cached input separately. These provisional review triggers scale the pilot's aggregate worker counters by 40/239, rounded upward; they are not prices, safe per-file limits, or forecasts for a different format mix. Before increasing width or adding a format, record wall time, uncached/cached input and output tokens, extraction bytes, failures, claim support checks, revisions and retrieval success on representative questions. Review at least one record per lane plus targeted high-risk formats and every failed/ambiguous import; the pilot's coordinator spot-check covered about 31 claims nonrandomly and found locator, coverage, HTML and image errors. It cannot estimate a population error rate or justify unattended acceptance. Stop or reduce a route when its measured cost exceeds its declared budget or unsupported claims persist after correction; record the threshold and decision in that run's receipt. No numeric monetary gate is asserted without a billing observation.

Migrate the manual survey by carrying forward its existing catalog UUIDs, inspections and coverage as history, not by replaying old observations as new evidence. Seed a new scoped manifest from a fresh `sinnix-fs` inventory; reconcile known paths and identity mismatches explicitly. The private pilot `extraction-index.json` may suggest recipes and artifacts, but every reused entry must pass current source and version checks. Retain the manual receipts for provenance. Implement in bounded packages: (1) manifest/cache owner and revision/lease schema in `pkgs/sinnix-fs/` plus focused synthetic tests; (2) deterministic format adapters and locator validation there; (3) reviewed semantic serializer and catalog/ledger import reconciliation in their existing packages; (4) declared AgentCTL operation and private state/retention configuration in the Sinnix module and descriptor. Each package needs its own focused verification before production enablement. This design change performs no activation or corpus scan.
