# Snapshot backup acceptance

The realm and persist drains retain each read-only Btrfs snapshot until a named Borg archive has been accepted. A successful create must have exit status zero; Borg warnings count as failure. Creation uses only declared static exclusions. Cache tags and `.nobackup` files cannot exclude a canonical directory.

Each wake captures one finite queue, processing the newest pending snapshot first and then historical states. Every accepted snapshot has its own durable acknowledgement beneath the latest marker's `.by-snapshot` directory. A newer archive cannot authorize deletion of an older snapshot. Release checks that snapshot's archive ID, UUID comment, coverage receipt, subvolume UUID, creation generation, subvolume ID and Btrfs filesystem UUID, then rechecks physical identity before deletion. Missing or invalid proof retains the snapshot. Receipt publication precedes latest-marker advancement, so an interrupted marker update can recover without recreating the archive. The newest acknowledged local snapshot remains available for the independent full audit. Creation generations order freshness even after a clock rollback; historical backfill cannot move the latest marker backward.

The realm drain accepts a fresh, warning-free create as a producer-backed proof, including its first archive. Before acknowledgement, it binds the Btrfs filesystem UUID and read-only snapshot UUID, generation and subvolume ID to Borg's create result, the archive's UUID comment and immutable ID, the exact create command, and a hash of the coverage policy. The policy includes Borg exclusion patterns after their bind-path qualification. This proves which immutable snapshot Borg reported archiving successfully. It does not independently compare all source and archive bytes.

Immediately after a successful realm create, the drain atomically writes an unacknowledged creation receipt. If the process stops before publishing the acknowledgement, a later drain can accept the existing archive only when that receipt still matches the snapshot, archive ID, policy and command. An older archive without a matching receipt gets a new `-producer-vN` name and a fresh create. No marker or prune follows a failed create, receipt check or proof.

Persist keeps an independent full proof on its first run, on policy changes, for preexisting archives and at least every seven days. Between those checks, a fresh successful create receives a producer-backed proof. Its full proof enumerates canonical source and archive paths, compares metadata, links, xattrs and ACL presence, checks archive health, and hashes regular file content on both sides. If a preexisting archive fails that comparison, persist creates a fresh `-coverage-vN` archive under the current policy and requires it to pass the full proof before acknowledgement. This lets old cache-tag exclusions fail closed without wedging the drain. The measured recent persist full proof took 43 minutes within its four-hour unit limit.

Realm's independent full proof runs in `borgbackup-coverage-audit-realm.service` with a 36-hour limit. Its hourly :35 timer compares the latest acknowledged snapshot when the successful receipt is at least seven days old or its policy changed. Lock contention or a pending current-policy acknowledgement records a deferred attempt and leaves the audit due. The shared Borg lock protects the selected snapshot from pruning throughout the comparison, and snapshot and archive identities are checked before and after it. Archive windows do not cancel this full comparison: lock-busy drains retain their queued snapshots without publishing new acknowledgements. The btrbk job uses `--preserve-snapshots`. Success writes `realm.independent-full-audit.json`; failure preserves the previous receipt. Runtime readiness reports missing, changed-policy and overdue proof separately from deferred attempts. An audit failure does not invalidate producer-backed archives.

The independent Realm audit keeps its disposable inventory and SQLite sort files in a private `coverage-scratch` directory under Borg's cache on `/persist`. Its inventory can grow beyond the remaining space on the audited filesystem. Completed comparisons remove their temporary inventory; interrupted inventory may remain for owner recovery.

The Realm drain has a 24-hour limit for multi-terabyte backfills under idle I/O and bandwidth caps. Persist retains its four-hour limit; the sequential coordinator allows 28 hours and 15 minutes. These budgets do not change archive acceptance or snapshot pruning guards. A timeout before proof retains queued snapshots.

The separate weekly `borgbackup-verify` job starts Sunday at 13:00. Its 4h30m deadline ends thirty minutes before the 18:00 archive window. It runs `borg check --repository-only --max-duration` for persist (1,800 seconds), realm (7,200 seconds), and Sinex blobs (1,800 seconds), then invokes the default `sinnix-borg-drill` script. That script adds the same check for persist and realm, with a limit of 1,800 seconds per repository. The configured check budgets total four hours. Command startup and finishing a segment can add some time. Borg resumes each repository from its saved segment cursor. These checks validate segment CRCs; they do not verify the repository index or encrypted archive contents. The manual `sinnix borg-drill --verify-data` option verifies archive data integrity, but it does not restore a file and the timer does not use it.

Manual archive-data verification fails with a diagnostic receipt when archive enumeration fails or returns malformed metadata. A successful empty listing remains a separate `no_archives` outcome. The selected archive is checked by its exact repository/archive address, so similarly prefixed names cannot substitute for it.

`agentctl job start sinnix verify_snapshot_restore -- --target <private-receipt.json> --version old` checks one file of at most 1 MiB under the bulk resource limits. The private input binds its archive ID, snapshot UUID, relative path, complete byte count and SHA-256. The operation verifies archive identity before and after extraction, caps retained output, and allows five minutes for Borg's complete metadata traversal. Job output contains the verified identities and digest, never the restored content. Its credential reference and environment come from the installed archive owner. This is a targeted restore proof, separate from full archive integrity or a whole-snapshot restore.

The realm repository had 2,635,872,968,704 bytes allocated on 2026-09-27. At the configured 40 MB/s read cap, its two weekly partial checks provide 9,000 seconds of progress, so a full CRC pass takes at least about 7.3 weeks. Lower throughput extends that cycle. The separate independent full realm audit compares an acknowledged snapshot with Borg content; the per-snapshot producer proof remains the gate for newly archived snapshots.

The acknowledgement records `proof_mode`, `policy_sha256`, snapshot and archive IDs, and creation and verification metrics. A fresh create logs `backup_phase=create`; every successful proof logs `backup_phase=verify`. The marker records creation time and Borg's logical original archive bytes, plus verification time and bytes hashed. The independent audit logs its own elapsed time and bytes. Borg's logical size is not a physical disk-read counter.

The machine telemetry SQLite dump is a separate producer for the realm drain. Its daily job freezes a checkpointed database in a read-only subvolume, checks that the SQLite header and schema open, compresses it, and tests the compressed frame before publishing. Its receipt reports `restore_check=zstd-t:ok`, `source_open=schema_header:limited`, and `structural_check=not_run`. The frame test validates decompression and its checksum; the schema check was made on the source before compression. Neither is a page-by-page integrity check. The direct-path Borg job restores an archived compressed dump to a stream and tests its frame before publishing its own freshness marker.

The weekly `machine-telemetry-sqlite-verify` job freezes a fresh WAL-free snapshot and runs a bounded SQLite structural walk without blocking the daily producer. Its journal receipt states the check and result. `structural-verification.status` in the dump directory records the latest attempt as running, failed, or ok, so the Borg dump archive carries the independent result alongside the artifacts. The capture lane requires `state=ok` and flags the result stale after eight days. Structural walks disable SQLite file mapping to avoid read-ahead amplification across interleaved B-trees. The check has a 150-minute query budget, a 160-minute unit limit, and a 100 MB/s read limit on `/realm`. This result applies to the independently frozen database state, not retroactively to every daily compressed artifact. A failed or overdue check leaves daily snapshots publishable and must be treated separately from their freshness.

With backups enabled, the verifier runs in the existing bounded `borgdrain.slice`, retaining its own 2 GiB memory pressure threshold and 4 GiB hard limit. This gives the structural walk working-set headroom alongside the independent coverage audit in `background.slice`. Idle I/O scheduling and device ceilings remain in effect; a ceiling does not guarantee throughput under competing load. Standalone telemetry installations without the backup owner retain the default backup-class slice.

A full-size retained telemetry dump can be restored and structurally checked with
`agentctl job start sinnix verify_telemetry_restore -- <exact-archive.sqlite.zst>`.
Run it separately from the independent snapshot scan. It pins the input file,
records its full SHA-256, bounds restored bytes to 80 GiB and requires that much
free job scratch plus a 2 GiB reserve. Decoding and checksum validation have a
one-hour acquisition budget; the restored database receives the existing
150-minute structural check. Its receipt applies to that exact compressed
artifact. Temporary restored bytes are removed with the job's private scratch;
original archives remain unchanged. A failed restore publishes no success receipt.
If a complete decoded image was retained for diagnosis, use `agentctl job start sinnix verify_telemetry_structure -- <exact-immutable.sqlite>` to repeat only its structural check. The source must be a closed regular file; passing a live database as immutable is invalid. A WAL lookup failure or nonregular sidecar refuses the operation; an empty regular sidecar is allowed. Its receipt describes that image, and does not replace frame validation of its compressed source.

Structural walks disable SQLite memory mapping and apply descriptor-local random-read advice to the open main database, avoiding speculative reads of unrelated interleaved pages. This does not change global device read-ahead, the integrity pragma, deadlines or resource limits. If the optional advice is unavailable, the structural check still runs and reports that limitation. Header-only publication does not take this route.

The declared telemetry verification operations resolve the checker package from the selected project's development environment. Select a candidate descriptor with `--project <checkout>`; `--workspace` changes the execution directory while retaining the registered project's operation declaration. The shell includes the source-built checker directly, so verification does not silently fall back to the installed `sinnix` dispatcher.

The weekly Btrfs metadata-image job captures persist, then realm, with a separate 40-minute window and at most three attempts per label. The unit has an 85-minute deadline, a 4 GiB memory pressure threshold, a 5 GiB hard memory limit, and no swap allowance. It inherits idle I/O scheduling and device bandwidth limits from the backup resource class. An image is published only after `btrfs-image` exits successfully and its temporary output passes the minimum-size check. A failed or timed-out attempt leaves earlier completed images in place and logs the affected label. This check does not establish that a metadata image can be restored; a controlled restore and a busy-desktop run remain operational verification.


The live model home is covered by default. Explicit acquired weight stores retain exclusions; authored control-vector outputs are protected against an exclusion of their directory or an ancestor. Historical `library/models` snapshot addresses retain their historical policy.

Coverage compares POSIX ACL numeric principals and permissions, including default
ACLs. Display names and entry order do not define identity. The policy fingerprint
includes this metadata contract, so a receipt from the former presence-only ACL
check cannot qualify the stronger proof. Existing receipts remain historical
evidence; a full comparison under the current contract must establish a new baseline.

The Polylogue state archive seals hooks from a read-only cut of its dedicated Btrfs state subvolume. The producer verifies the source and cut UUIDs, the cut's parent UUID and read-only flag, and refuses nested subvolumes that a snapshot would omit. Writers continue against live state while the sealer reads the cut. Unsupported reflinks, including NoCoW-to-CoW copies, stream from that immutable cut with a bounded buffer. Source identity and size checks, metadata preservation, fsync and atomic cache publication apply to both paths. Its durable cache keeps the existing logical archive paths and strict per-file and whole-tree checks. Verified origin UUIDs allow reuse across cuts despite device-number changes; inode and change metadata must still match. Failed provisional cuts remain in the private hook cache for owner recovery. Successful sealing removes only that invocation's verified cut before Borg creation. This cache cleanup does not prune historical restore points or change archive acceptance.
